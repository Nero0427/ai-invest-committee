## 动手搭建：AI 投委会原型（ai-invest-committee/）

用户提出「搭一个看看」。环境探测结果：无 Docker、无 git、无任何 LLM API key，只有托管 Python 3.13.14 和 Node 22.22.2。因此放弃官方 TradingAgents-CN 的 Docker 路线，改用纯标准库自建，零第三方依赖。

产物位于 `ai-invest-committee/`：
- `datasource.py` — 行情与指标层，东方财富为主源、腾讯为备源，均无需 API key
- `agents.py` — 8 个 Agent 角色定义 + 投委会编排 + 无 key 时的规则引擎降级
- `llm.py` — OpenAI 兼容适配层，内置 8 家服务商预设（DeepSeek/GLM/Qwen/Kimi/硅基流动/OpenAI/Ollama/自定义）
- `settings.py` — 配置加载，对外隐藏 api_key
- `server.py` — 标准库 HTTP + SSE 流式服务端
- `static/` — 深色三栏界面，复刻截图布局
- `start.bat` — 双击启动

关键技术结论（下次直接复用，省大量试错）：
- 东方财富接口会随机抛 RemoteDisconnected，**必须加请求节流**（实测 0.25s 间隔可稳定）
- 东财 secid 规则：沪市 `1.代码`、深市/北交所 `0.代码`、美股 `105.纳指 / 106.纽交所 / 107.美交所`
- 美股 secid **不要逐个探测**：先用腾讯 `qt.gtimg.cn/q=us代码` 取交易所后缀（.OQ→105、.N→106），一次请求即可映射
- 腾讯行情字段以 `~` 分隔：3=现价 4=昨收 5=今开 6=量 33=最高 34=最低 44=流通市值(亿) 45=总市值(亿)；A 股 39=PE、46=PB，美股 47=PE
- 腾讯 K 线：`web.ifzq.gtimg.cn/appstock/app/fqkline/get?param=sh600519,day,,,N,qfq`，数据在 `qfqday`；A 股后缀 sh/sz，美股需加交易所后缀
- 规则引擎要有**对称的置信度锚点**：按证据条数直接计数会让多头获得结构性优势，改为按分析师团队净倾向 bias 对称生成

验证状态：数据层、Agent 编排、HTTP+SSE 全链路均已跑通（LITE 美股与 600519 A 股）。**真实大模型调用路径未验证**，因为环境内没有任何 API key；用户在界面「设置」里填入 key 即可切换，无需改代码。

### 关于东方财富限流（重要，避免重复踩坑）
- 东财限流**按 IP + 按域名分别计算**，`push2`（行情/列表）宽松，`push2his`（K线）极严。
- 实测：连续请求 20 次后 push2his 会被封 30 分钟以上，股票和板块 K 线一起挂；`push2` 只短暂受限。
- **镜像域名不解决问题**：扫过 `1/2/3/5/7/9/11/13/17/29/43/57/73/82.push2his`，只有 `1.push2his` 偶尔可用，且照样受频率限制。
- 结论：**K 线一律不要依赖东财**，节流设 1.2s 也只是缓解。

### 突破：腾讯 newfqkline 统一 K 线源
`https://proxy.finance.qq.com/ifzqgtimg/appstock/app/newfqkline/get?param={code},day,,,250,qfq`
- 一个接口覆盖 A 股（`sh600519`）、美股（`usXLK.AM`）、**板块指数（`pt01801120`）**，全部返回 250 根日线，且完全不受限流影响。
- 数据键名：A 股是 `qfqday`，美股和板块是 `day`。
- 旧的 `web.ifzq.gtimg.cn/.../fqkline` 对板块只返回 1 根，别用。
- 美股必须带交易所后缀（`.OQ` 纳斯达克 / `.N` 纽交所 / `.AM` 美交所）；不带后缀不会报错，而是静默返回 1 根，所以必须用长度校验兜住。

## 第四轮：金十快讯扩容到 1000 条

用户反馈"直接相关 0 条"，要求把快讯量从 60 提到 1000。

### 关键事实（下次直接用）
- 金十接口**固定返回 21 条/页**，`count` / `limit` / `size` / `page_size` **全部无效**，只能靠 `max_time` 串行翻页。
- **翻页完全不限流**：实测连续 55 页、1101 条、13.9 秒无任何拒绝。这是少数不需要节流顾虑的接口。
- 1000 条覆盖约 **2.5 天**的快讯，其中重要快讯约 177 条。
- 翻页间隔 0.12s 即可，实测 1000 条 8.5 秒。

### 实现要点
- **磁盘缓存 + 增量刷新**是关键。`_walk()` 从最新往回翻，一旦遇到已缓存的 id 就立刻停止——因为快讯是倒序追加的，最新的几页必然覆盖全部新增内容。
- 效果：首次全量 8.5s，内存缓存 0.000s，**增量刷新仅 0.1s（1 个请求）**。
- 服务启动时后台线程 `warm_cache()` 预热，避免首次分析多等 10 秒。
- **一个隐蔽的坑**：增量刷新时不能拿 `seen`（本页出现过的所有 id）去过滤旧缓存，否则每刷新一次列表就少 20 条。必须用 `fresh`（真正新增的 id）去过滤。我一开始用错了，1000 条悄悄变成 981 条。
- **另一个坑**：如果缓存的条数本身不足目标值，就不能把它当作"翻页终点"——否则永远补不满。要判断 `len(previous) >= limit` 才启用增量模式。

### 效果
半导体板块匹配从 **0 条 → 12 条**，科技板块 15 条（上限）。白酒这类当期确实没有新闻的板块仍为 0，但宏观要闻能补 15 条。

### 几个必须知道的坑

**1. `last.js` 只有 140 根。** 要 250 根必须拼接年份文件（`2026.js` 169 根 + `2025.js` 243 根）。
`all.js` 返回的是另一种结构（`price`/`volumn`/`dates` 数组），不能当 K 线用。

**2. 板块代码要枚举，而且存在「有名字没行情」的僵尸板块。** 首次只扫 `886000-886060`
命中 61/61，差点误判为「概念板块都在 886xxx」—— 实际主力是 `885xxx`（命中 344 个），
`886xxx` 只有 112 个。全扫 1899 个编号后得到约 554 个有名字的，其中 `885284 稀缺资源`、
`885420 电子商务` 这类**返回了名称但 `data` 为空**（已停更），必须用「有没有 K 线」过滤掉，
否则板块能选中、分析必然失败。过滤后存活 **480 个（行业 90 + 概念 390）**。

**3. 实时行情的字段是内部数字编号，没有文档。** 靠跟腾讯的同一只股票逐字段对照推出来的
（600519 双跑，8 个字段全部吻合）：`6`=昨收 `7`=今开 `8`=最高 `9`=最低 `10`/`30`=现价
`13`=成交量 `19`=成交额 `199112`=涨跌幅 `2034120`=PE `592920`=PB `3475914`=总市值。
个股名称在 `items.name`，板块没有（板块名要另取，所以 `realhead` 的 `name` 不能当通用字段用）。

**4. 成交量单位是「股」，不是「手」。** 东财、腾讯都用手，不转换绝对量值差 100 倍。
校验方法：`成交额 ÷ 成交量 = 每股价格`，用 600519 的 K 线验证过。入库前统一 ÷100。

**5. 板块 ID 和指数代码是两套编号。** 概念板块页面用 `308614` 这种 ID，
指数代码却是 `886056`（阿尔茨海默概念）—— 页面 HTML 里能抓到对应关系，但只有取成分股时才需要，
本次没用上。

### 为什么成分股故意没换

用户要求「全量替换」，但成分股这一层保留东财，理由是实测数据：

- 同花顺：服务端渲染的 HTML 表格，概念板块 **10 只/页**、行业 20 只/页，一个 100 只成分股的
  概念板块要翻 10 页；且字段只有代码/名称/现价/涨跌幅/换手/量比，**没有市值**。
- 东财 `clist`：一次请求给 500 只，自带市值、PE、资金流向（`f62`），而且它所在的 `push2` 域
  **从来不是被限流的那一层**（被限的是 `push2his`）。

换过去的代价是请求数涨十倍、字段反而变少。所以取长补短：同花顺管行情与历史，东财管成分股。
两者按**板块名称**做映射，480 个板块匹配上 347 个（72.3%）；匹配不到的仍有完整指数 K 线。

名称匹配沿用了原有的「精确优先 + 有界包含」策略（`银行` 不能匹配到 `银行系保险`）。

## 第八轮：大盘云图 + 补齐左侧全部页面

### 先说那两个 bug（都是真 bug，不是错觉）

**1. 板块列表被硬截断到 80 条。** `server.py` 里写死 `items[:80]`，而行业有 90 个、概念 390 个 ——
所以不管打开哪个标签页都只能看到 80 个。改成 1000 后行业 90、概念 390 全部出来。

在任何人的耐心下都表现为「一直加载中」。四处修复：

- 板块表构建改成**启动时后台预热**（跟新闻缓存一样的做法）
- 扫描并发 4 → 16（29 秒 → 6 秒）

### 大盘云图

参考站 52etf.site 是 Nuxt + TreeMap 组件，页面上 preconnect 到 `push2delay.eastmoney.com`、
`dq.10jqka.com.cn`、`gateway.jrj.com`。顺着这条线索摸到东财的延迟行情主机。

**为什么用 `push2delay` 而不是 `push2`**：实测 `push2` 对全市场查询直接
`Remote end closed connection without response`，而 `push2delay` 稳定返回 ——
代价是约 15 分钟延迟，这在热力图上根本看不出来。

**60 页拿全市场**：接口一页只给 100 行（`pz=500`/`pz=1000` 都无效），全市场 5913 行。
10 线程并发分页，0.89 秒拿完。

**只画市值前 1500 只**：再往下的小票在画布上是像素级的存在，全发过去会让 JSON 从 111KB 涨到
400KB 以上，换不来任何可读性。覆盖 84% 总市值，这个数字直接显示在页面上，不让人猜。

**树图算法自己写**：squarified treemap（Bruls / Huizing / van Wijk），约 50 行。
项目坚持零依赖，引一个图表库就破了这个规矩。

**踩了两个连着的坑，都是 viewBox。** 最初用固定 `0 0 1000 620` + `preserveAspectRatio="none"`，
文字被非等比拉伸；改成按容器实际像素测量后，又遇到第二个问题 —— 测量发生在龙虎榜渲染**之前**，
当时容器高 664px，等下方龙虎榜渲染完，`flex: 1 1 auto` 把它压到 380px，
viewBox 与实际视口比例不符，整张图被缩小居中，两侧大片留白。

解法两步：容器高度改成固定的 `clamp(380px, 54vh, 640px)`（不跟着内容伸缩），
再加 `ResizeObserver` 在尺寸变化时**用已有数据重绘**（不重新请求）。现在窗口怎么拉都不变形。

## 第九轮：改名、砍页面、云图加美股、龙虎榜加席位

### 「Failed to fetch」的真凶

用户报大盘云图和龙虎榜都「加载失败：Failed to fetch」，但云图本身画出来了 ——
说明 `/api/treemap` 成功，只有 `/api/market` 和 `/api/billboard` 挂。

先怀疑冷启动并发，写脚本清空 cache 再并发打三个接口：**全都成功**。排除。

真凶在 `HTTPServer.request_queue_size`，**stdlib 默认值是 5**。浏览器打开一个页面会在同一瞬间
发起文档、两个脚本、样式表、favicon，超出的连接在后备队列里放不下就被直接 reset ——
服务端**根本没看到这个请求**，前端只能报 "Failed to fetch"。
自定义了一个 `Server` 子类把队列提到 128。

这类 bug 的特点是**服务端日志干干净净**，因为它压根没进到处理函数。
